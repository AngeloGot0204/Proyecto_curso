## Technical Approach

Stock Django 5.2 LTS scaffold generated by `startproject config .` (which already yields the single `config/settings.py` required by decision 5), one `usuarios` app holding `Usuario(AbstractUser)`, and stock `LoginView`/`LogoutView` behind the default `registration/login.html` path. Everything environment-specific arrives through `.env` so the same `config/settings.py` works unchanged when item #2 injects real environment variables on Vercel.

The one non-mechanical decision is how `rol == administrador ⇒ is_staff = True` is enforced. This design answers it with a **derive-plus-backstop** pair: `Usuario.save()` derives the flag, two `CheckConstraint`s make the invariant unbypassable at the database level.

Domain identifiers stay Spanish (`Usuario`, `rol`, `administrador`) because TECH-DESIGN's data model names them that way; prose, comments, and test names are English.

## Architecture Decisions

### Decision 1: `rol` is the source of truth; `is_staff` is derived

**Choice.** `rol` is authoritative and operator-editable. `is_staff` is a computed mirror, never edited by hand. In `Usuario.save()`, in this exact order:

```python
def save(self, *args, **kwargs):
    if self.is_superuser:            # superuser wins over rol
        self.rol = Rol.ADMINISTRADOR
    self.is_staff = self.rol == Rol.ADMINISTRADOR   # biconditional
    super().save(*args, **kwargs)
```

Backed by two named constraints in `Meta.constraints`:

| Constraint | Condition |
|---|---|
| `usuario_rol_implica_is_staff` | `Q(rol=ADMIN, is_staff=True) \| (~Q(rol=ADMIN) & Q(is_staff=False))` |
| `usuario_superuser_es_administrador` | `Q(is_superuser=False) \| Q(rol=ADMIN)` |

**Resolved semantics** (these are the questions item #13 must not have to guess):

| Situation | Result |
|---|---|
| `rol` set to `administrador` | `is_staff = True` |
| `rol` downgraded `administrador → usuario` | `is_staff` **is revoked** (`False`). The invariant is a biconditional, not one-way — otherwise a demoted admin keeps Django-admin access, which is exactly the drift decision 2 forbids. |
| `is_superuser = True` (e.g. `createsuperuser`) | `rol` forced to `administrador`, therefore `is_staff = True`. |
| Demoting a superuser to `rol = usuario` | Silently re-promoted. To demote, clear `is_superuser` first, then set `rol`. This is the single documented exception where a flag overrides `rol`. |
| New user, `rol` unspecified | `default = Rol.USUARIO` — least privilege. |

**Consequence for decision 7**: `manage.py createsuperuser` needs **no** manual follow-up. It sets `is_superuser=True`, `save()` forces `rol=administrador` and `is_staff=True`. `rol` is deliberately **not** added to `REQUIRED_FIELDS`, since prompting for it would let an operator create a self-contradictory `superuser + rol=usuario`.

**Alternatives considered.**

| Option | Bypassed by | Verdict |
|---|---|---|
| `save()` override *(chosen, layer 1)* | `QuerySet.update()`, `bulk_create`, `bulk_update`, raw SQL, `loaddata` (`save_base(raw=True)`) | Chosen: covers every ordinary write path (admin forms, `createsuperuser`, shell, tests) and can *repair*, not just reject. |
| `post_save` signal | Identical bypass set, **plus** it needs a second DB write and an `update_fields` recursion guard | Rejected: same coverage as `save()` at higher cost and lower locality. |
| `clean()` / `full_clean()` | Any plain `.save()` — shell, tests, data migrations, `createsuperuser` | Rejected: only runs under ModelForm validation, and can only reject, never derive. Weakest coverage of the four. |
| `CheckConstraint` *(chosen, layer 2)* | **Nothing.** Enforced by PostgreSQL on every write path including `update()` and raw SQL | Chosen as backstop, not as the primary: it raises `IntegrityError` rather than repairing, so alone it would make ordinary admin edits fail. |
| `is_staff` as a Python `@property` (no column) | n/a | Rejected: Django forbids shadowing a field inherited from `AbstractUser`; would force `AbstractBaseUser`, contradicting decision 1. |

**Admin UX consequence.** `UserAdmin`'s Permissions fieldset renders `is_staff` as an editable checkbox that `save()` would silently overwrite. `UsuarioAdmin` therefore puts `is_staff` in `readonly_fields` so the operator sees it as derived rather than fighting it.

### Decision 2: dependency manifest — `requirements.txt` (+ `requirements-dev.txt`)

Chosen over `pyproject.toml`: the project ships no installable package, the developer is solo and Python-primary, and Vercel's Python builder (item #2) detects `requirements.txt` natively with zero configuration. Split into two files so item #2's production build never installs pytest — a 3-line cost.

| File | Pins |
|---|---|
| `requirements.txt` | `Django>=5.2.8,<6.0` (LTS, security support to 2028; 5.2.8 is the floor for Python 3.14) · `psycopg[binary]>=3.2,<4` (prebuilt wheels — no C toolchain on Windows) · `python-dotenv>=1.0,<2` · `dj-database-url>=2.2,<3` |
| `requirements-dev.txt` | `-r requirements.txt` · `pytest>=8,<9` · `pytest-django>=4.9,<5` |

### Decision 3: environment loading — `python-dotenv` + `dj-database-url`, fail-loud

`python-dotenv` does exactly one thing (load `.env` into `os.environ`) and is the library the developer will meet outside Django too; `dj-database-url` turns Neon's exact `postgresql://…?sslmode=require` string into a `DATABASES` dict. Rejected `django-environ` (one dep instead of two) because its `default=` parameter makes silent fallbacks the path of least resistance — the opposite of what we want.

Fail-loud is explicit and lives in project code, not a library default:

```python
def require_env(name):
    try:
        return os.environ[name]
    except KeyError:
        raise ImproperlyConfigured(f"Missing required environment variable: {name}")
```

| Variable | Behavior when missing |
|---|---|
| `DJANGO_SECRET_KEY` | `ImproperlyConfigured` at import — startup fails |
| `DATABASE_URL` | `ImproperlyConfigured` at import — startup fails |
| `DJANGO_DEBUG` | Defaults to `False` |
| `DJANGO_ALLOWED_HOSTS` | Defaults to `localhost,127.0.0.1` |

Only the two variables whose default is the *restrictive* direction get a default, so a missing value can never accidentally loosen security.

**Forward-compat hook (noted, not designed — item #2):** `load_dotenv()` does not override already-set environment variables and is a silent no-op when `.env` is absent, so the identical `config/settings.py` works on Vercel with no `.env` file.

### Decision 4: URL routing — explicit two-path `usuarios/urls.py`

```
config/urls.py
  admin/   -> admin.site.urls
  ""       -> include("usuarios.urls")

usuarios/urls.py
  login/   -> LoginView.as_view()    name="login"
  logout/  -> LogoutView.as_view()   name="logout"
  ""       -> inicio                 name="inicio"   @login_required
```

Rejected `path("accounts/", include("django.contrib.auth.urls"))`: it silently publishes the password-reset views, which need an email backend the proposal explicitly excludes — a user reaching `/accounts/password_reset/` would hit a dead or erroring flow. Explicit paths expose exactly what is in scope.

**Design addition — `inicio` placeholder.** The proposal has no post-login landing page (S-02 belongs to item #12), so `LOGIN_REDIRECT_URL` would 404 and the proposal's own success criteria would be unverifiable. This design adds a ~10-line `@login_required` view rendering `templates/inicio.html` (username + logout button). Scope guard: item #12 replaces it; it must accumulate no report logic.

**Django 5 gotcha:** `LogoutView` requires POST since 5.0. The logout control is a `<form method="post">` with `{% csrf_token %}`, not a link. Item #5 inherits this from `base.html`.

Settings: `LOGIN_URL = "login"`, `LOGIN_REDIRECT_URL = "inicio"`, `LOGOUT_REDIRECT_URL = "login"`, `SESSION_COOKIE_AGE = 604800`.

### Decision 5: templates — stock `registration/login.html`

`templates/registration/login.html` is `LoginView`'s default `template_name`, so no `template_name=` wiring is needed. This supersedes the proposal's `templates/usuarios/login.html` path (a refinement, not a scope change) and matches ADR-0005's "stock views/forms".

`templates/base.html` is deliberately minimal — doctype, `{% block title %}`, `{% block extra_head %}`, `{% block content %}`. No CSS framework, no JS. It exists only so item #5 extends something instead of inventing a base mid-wizard.

Login body: `{% csrf_token %}`, `{{ form.non_field_errors }}`, `{{ form.as_p }}`, submit, and the static note "Solicita tu cuenta al administrador" (DESIGN S-01).

**Two knowing deviations from DESIGN S-01, recorded so verify does not flag them as defects:** the configurable institutional logo depends on `TipoDeReporte` + Blob storage (items #2/#13) and is omitted entirely — no placeholder logic; and S-01's "usuario/correo" is settled as username-only by decision 3.

### Decision 6: pytest configuration and the Neon test-database problem

`pytest.ini` at the project root (no `pyproject.toml` exists by decision 2; `setup.cfg` is legacy):

```ini
[pytest]
DJANGO_SETTINGS_MODULE = config.settings
python_files = test_*.py
addopts = --reuse-db
norecursedirs = .venv .git .pytest_cache
```

**The Neon concern, addressed.** pytest-django creates `test_<dbname>` on the configured server, so tests run over the network against the Neon dev branch.

| Problem | Mitigation |
|---|---|
| Latency (~20–80 ms per round trip) | `--reuse-db` in `addopts` creates the schema once and reuses it. Each test still runs in a rolled-back transaction, so no data leaks. In-scope suite is ~12 tests — seconds, not minutes. |
| Two concurrent runs colliding on the same `test_` database | `DATABASES["default"]["TEST"] = {"NAME": os.environ.get("TEST_DB_NAME", "test_reportes_dev")}` — each developer or future CI runner sets a distinct value. Two lines, no new infrastructure. |
| Latency becoming intolerable later | Escape hatch is already free: point `DATABASE_URL` at a local PostgreSQL in `.env` for the test run. **No code change**, because the URL already comes from the environment. Not built now. |

Rejected SQLite-for-tests: it would silently pass constructs PostgreSQL rejects and defeats decision 4's one-engine rationale (item #10 needs a real DB sequence).

**Test gotcha to carry into tasks:** the constraint tests assert `IntegrityError` from `QuerySet.update()`. Each must be wrapped in its own `transaction.atomic()` block, or the poisoned transaction breaks every subsequent assertion in the test.

**Exact command for `sdd/proyecto/testing-capabilities` to record:**

- Run: `python -m pytest` (project root, venv active — `python -m` avoids Windows PATH ambiguity)
- After model changes: `python -m pytest --create-db`

### Decision 7: migration ordering

The hard gate: **the very first `migrate` must run only after `AUTH_USER_MODEL` is set and `usuarios/migrations/0001_initial.py` exists.** Django's `auth` and `admin` migrations declare `swappable_dependency(settings.AUTH_USER_MODEL)`, so once `0001_initial` exists the graph orders it first automatically — but if `migrate` runs first, PostgreSQL gets `auth_user` plus `django_admin_log.user_id -> auth_user`, and recovery is not "delete a file".

| # | Step | Guard |
|---|---|---|
| 1 | `git init`, write and stage `.gitignore` (excluding `.env`) | Before `.env` exists, so the credential is never trackable |
| 2 | `git remote add origin https://github.com/AngeloGot0204/Proyecto_curso.git` | No push (decision 8) |
| 3 | `python -m venv .venv`; `pip install -r requirements-dev.txt` | |
| 4 | `django-admin startproject config .`; `python manage.py startapp usuarios` | Yields `config/settings.py` as a module — matches decision 5 with no restructuring |
| 5 | Edit `config/settings.py`: `INSTALLED_APPS += ["usuarios"]`, **`AUTH_USER_MODEL = "usuarios.Usuario"`**, `DATABASES`, `TEMPLATES["DIRS"]`, session/login settings | |
| 6 | Write `usuarios/models.py` | |
| 7 | **Pre-flight**: `usuarios/migrations/` contains only `__init__.py`, and `python manage.py showmigrations` lists everything unapplied | If the Neon branch already has tables, reset the branch or `DROP SCHEMA public CASCADE; CREATE SCHEMA public;` — a local file delete is not enough for a network DB |
| 8 | `python manage.py makemigrations usuarios` -> `0001_initial.py` | Inspect: creates `usuarios_usuario`, not `auth_user` |
| 9 | `python manage.py migrate` | |
| 10 | `python manage.py createsuperuser` | Verify `rol == administrador` and `is_staff is True` with no manual fix |

Steps 11+ (views, templates, tests) have no ordering constraint.

## Data Flow

Login path:

```
Browser                config.urls        usuarios app              Postgres (Neon)
  │ GET  /login/  ────▶ usuarios.urls ──▶ LoginView
  │ ◀──────────────────────────────────── registration/login.html
  │ POST /login/  ────▶                   AuthenticationForm
  │                                       authenticate() ────────▶ SELECT usuarios_usuario
  │                                       login() -> session ────▶ INSERT django_session
  │ ◀── 302 /  ·  Set-Cookie sessionid (max-age 604800)
  │ GET  /       ────▶                    inicio @login_required ▶ SELECT session + usuario
```

Invariant enforcement on every write:

```
admin form · createsuperuser · shell · tests
        │
        ▼
   Usuario.save()   if is_superuser -> rol = administrador
        │           is_staff = (rol == administrador)
        ▼
   INSERT / UPDATE ──▶ CHECK usuario_rol_implica_is_staff
        ▲              CHECK usuario_superuser_es_administrador
        │
  bypasses save(): QuerySet.update() · bulk_update · raw SQL · loaddata
        └────────── still caught by the CHECK constraints (IntegrityError)
```

## Interfaces / Contracts

```python
class Rol(models.TextChoices):
    ADMINISTRADOR = "administrador", "Administrador"
    USUARIO = "usuario", "Usuario"

class Usuario(AbstractUser):
    rol = models.CharField(max_length=20, choices=Rol.choices, default=Rol.USUARIO)

    @property
    def es_administrador(self) -> bool:      # the flag later items branch on
        return self.rol == Rol.ADMINISTRADOR
```

Contract fixed for items #3–#14: FK with `settings.AUTH_USER_MODEL` (never `Usuario` imported directly); authorize app-level admin actions on `user.es_administrador`, never on `is_staff`.

## Testing Strategy

| Layer | What to test | Approach |
|---|---|---|
| Unit — model | Default `rol` is `usuario`; setting `administrador` sets `is_staff`; downgrade **revokes** `is_staff`; `create_superuser` forces `rol=administrador` | pytest-django `@pytest.mark.django_db`, direct `.save()` |
| Unit — constraint | `Usuario.objects.filter(...).update(rol=ADMIN)` raises `IntegrityError`; `update(is_staff=False)` on an admin raises `IntegrityError` | Each inside its own `transaction.atomic()` |
| Integration — login | Valid credentials -> 302 to `inicio`; bad password -> 200 with form error; `rol=administrador` reaches `/admin/`; `rol=usuario` is refused `/admin/`; POST logout ends the session; `settings.SESSION_COOKIE_AGE == 604800` | Django test `Client` via pytest-django `client` fixture |
| E2E | None | No browser/offline surface in this change (items #9/#10) |

## Non-Goals (explicit)

- **Offline-tolerant session behavior** (ADR-0005's offline half) — items #9/#10. This change's only obligation toward it is `SESSION_COOKIE_AGE = 604800` and keeping login views free of side effects that could destroy a local draft.
- **Deployment, Vercel, production settings, Vercel Blob, Neon prod branch** — item #2. Two forward-compatibility hooks are *noted only, not designed*: `load_dotenv()` is a no-op without a `.env` and does not override real environment variables; `DJANGO_DEBUG`/`DJANGO_ALLOWED_HOSTS` are already env-driven.
- **Any report-domain model** (`TipoDeReporte`, `DefinicionDeTipo`, `Reporte`, `ValorDeReporte`, `CambioDeValor`, `Adjunto`, `VistoBueno`, `Generacion`) — items #3 onward.
- **Custom admin screens for report types (S-14)** — item #13. S-13 user management is served by stock `django.contrib.admin`.
- **Self-service password reset** — admin sets passwords directly in the Django admin; no email backend.
- **`git push`** — not authorized by decision 8; no push step designed.
- **Wizard UI / styling** — item #5. `base.html` carries no CSS framework.
